# 根因证据链与多节点时间线（必读）

## 1. 区分五层事实

1. **观测（Observation）**：日志原文、文件、行号、原时间戳、进程/设备/rank。
2. **症状（Symptom）**：任务退出、请求 504、HCCL 通信超时、设备不可用。
3. **触发事件（Trigger）**：直接导致症状的上游异常，如 rank3 进程被 OOM killer 杀死。
4. **根因（Root cause）**：为什么 trigger 发生，如容器 cgroup 限制小于峰值 RSS；需要独立证据或复现。
5. **处置与验证**：短期恢复、永久修复、如何证明修复有效。

引用通过 `verify` 仅代表 Observation 为真，不代表 Root cause 为真。结论状态至少标明 `观察属实/因果待证/根因已验证`，并说明证据缺口。

## 2. 事件格式

```json
{
  "event_id": "E1",
  "file": "node-a/train/rank3.log",
  "line": 1821,
  "timestamp_raw": "2026-10-17 10:01:02.123",
  "timestamp_normalized": null,
  "clock_uncertainty_ms": null,
  "host": "node-a",
  "pid": 12033,
  "rank": 3,
  "device": 3,
  "layer": "framework",
  "stage": "runtime",
  "kind": "process_exit",
  "quote": "Killed process 12033",
  "quote_verification": "PENDING",
  "interpretation": "进程退出，需核验是否真正为 OOM killer"
}
```

`timestamp_normalized=null` 表示未完成时区/偏差校正，不允许跨机按原字符串作根因排序。设备日志中的硬件时间与 Host 时间也应视为不同时间源。

## 3. 多机根因候选排序规则

- 将 **故障产生节点** 与 **最先报告超时节点** 区分：集群超时的本地报告时刻通常晚于实际卡住的时刻。
- 优先考虑可独立验证的事件：Python fatal stack、cgroup OOM、设备 RAS、进程异常退出、变更、网络端对端计数器，而不是重复打印的泛化 `ERROR`。
- 比较同一 rank 的最后正常迭代、最近 collective/tag，是否有异步误报：后一次 synchronize 报错可能对应更早的算子。
- 必须寻找竞争假设（至少 2 个）及其反证；不能只贴相同关键词、无证据直接断言版本缺陷。
- 无法对齐时钟时输出**每机局部时间线**与事件依赖图；禁止硬合成唯一时间顺序。
- 不允许把 absence-of-log 当成 absent-event：日志采样、轮转、缓冲、时段缺失、容器重启都可能造成空白。

## 4. 报告主张等级

- **A：根因已验证**：日志证据真实性 PASS；存在独立可复现/实验/交叉印证的因果链；有反证排除。
- **B：高概率**：有多条相互独立证据和合理传播关系，但未复现或未排除全部备选。
- **C：可能**：只有相关性与部分证据，明确必须补采什么和如何证伪。
- **D：未知**：仅有症状或时间线无法对齐；不给具体“确定根因”。

保持旧版 `[已验证]/[推断]/[待确认]` 三标记用于**证据引用**的验证状态，新增 A/B/C/D 用于**根因因果**的可信等级，不能混为一谈。

## 5. 安全的动作排序

`只读信息核验 → 小范围低风险实验 → 已批准的隔离/迁移 → 高风险变更（另行审批）`。包括清缓存、重置 NPU、重启进程/节点、更新驱动、清理日志、修改网络和长期提升日志级别，默认都**不自动执行**。

## 6. 失败与停止条件

- 无法确认受影响任务时，先报告已观察的异常和候选映射，不要求用户一次性交齐所有信息。
- 关键日志缺失时输出精确缺口和最小采集指令，不把其他日志的时间缺失推断为无故障。
- 脚本若提示 `retained < matched` 或 `truncated`，**不得宣称已完整枚举错误/全量最早错误**；需要缩窄时段、使用无截断参数重新提取或对重点模式二次扫描。
- 保密优先：日志和环境变量可能含 token、密码、客户 IP，公开报告前先按审批要求脱敏；保留稳定占位 ID 以便关联。
